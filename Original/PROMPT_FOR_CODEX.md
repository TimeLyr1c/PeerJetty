# 交给 Codex 的任务 Prompt

请继续完成并在我的 MacBook 上安装/验证一个原生 macOS 应用 `OpenOnMini`。我会同时提供一个 `OpenOnMini-Starter` 源码包；请优先检查并复用其中已经完成的 AppKit UI、图标、构建脚本和 SSH/SCP 传输逻辑，不要从零重写，也不要删除已工作的行为。

## 使用环境与必须先确认的信息

- 投放应用只运行在这台 MacBook 上。
- Mac mini 只作为接收端，绝对不要在 Mac mini 上启动或安装投放应用。
- 接收端 SSH 地址必须改成我自己的真实值：`<Mac-mini-用户名>@<Mac-mini-主机名>.local`。
- Bundle ID 必须改成属于我的唯一值，例如 `com.<我的名字>.OpenOnMini`，不要保留模板的 `com.example.OpenOnMini`。
- 在改代码前检查当前 MacBook 的屏幕、刘海安全区和缩放比例。不要硬编码另一台电脑的绝对屏幕坐标。
- 如果 SSH 地址、Bundle ID 或接收端用户名无法从当前环境可靠确认，请只向我询问这些必要值，不要猜。

## 产品行为

1. App 是原生 AppKit macOS 应用，平时完全隐藏，不显示 Dock 图标，也不显示菜单栏图标。
2. 当我从 Finder 或微信拖起文件时，屏幕刘海下方出现一个黑色投放区；它的宽度贴合真实刘海，像刘海向下延长。
3. 投放区平时不可见，普通点击鼠标不能触发它；只有有效文件拖拽才显示。
4. 展开和收回都有自然动画，底部圆角模拟真实刘海。成功状态保持约 0.5 秒后收回。
5. 当前 Starter 已针对同款 Retina 刘海屏做了一个边缘修正：保持右边缘不动，左边缘额外向左延伸 1 个物理像素。请保留以 `1 / backingScaleFactor` 计算物理像素的方式，不要写死 0.5 pt。
6. 接收普通文件 URL，同时保留 `NSFilePromiseReceiver` 支持。必须用真实 Finder 和微信拖拽分别测试，并记录实际 pasteboard 类型。
7. 微信容器文件采用直接读取方案；App 需要“完全磁盘访问权限”。不要重新引入 Finder 自动化、Automator 快速操作或复杂的临时复制绕行。
8. 文件通过系统现有的 SSH 密钥和 SCP 发送到接收端 Mac mini 的 `~/Downloads`。
9. 自动解决同名冲突：`文件.ext`、`文件 (1).ext`、`文件 (2).ext`，目录和隐藏文件也要正确处理。
10. 普通文件传输后在 Mac mini 上自动打开。如果没有应用能打开，传输仍算成功，只在刘海小窗显示“已发送，无法打开”，不要弹系统警告框。
11. `.app`、`.pkg`、`.mpkg`、`.dmg`、`.command`、`.tool` 以及带可执行权限的文件传过去后绝对不要运行，只用 Finder 显示。
12. App 第一次启动时只在后台运行，不自动打开设置。
13. App 已运行时再次双击打开，才显示设置面板。
14. 设置面板必须包含：SSH 地址、保存、测试连接、显示投放区预览、登录时自动启动开关、退出应用。
15. 登录时自动启动使用 `SMAppService.mainApp`，不要用旧式 LaunchAgent 脚本。
16. 设置窗口使用源码包自带的图标和原生 macOS 控件。

## 权限与安装

- 构建后把实际运行的 App 固定在一个不会再变化的位置，再为它开启“系统设置 → 隐私与安全性 → 完全磁盘访问权限”。
- 这是本地开发签名的 App；如果重新构建后微信访问权限失效，应删除系统设置里的旧条目，再加入新构建的 App。
- 不要保存 SSH 密码，不要把密码写入代码、脚本或日志。
- 不要创建或保留 Automator 快速操作。
