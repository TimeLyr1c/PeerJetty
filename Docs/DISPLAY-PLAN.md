# 无刘海屏幕投放入口调整方案

日期：2026-10-05。用户反馈：mini 的普通显示器上出现悬浮黑框，且没有贴住屏幕上沿。本文件是下一步界面方案，0.2.3/build5 只替换图标，尚未实现以下行为。

## 已确认的源码原因

DropPanelController.geometry() 对无刘海屏幕使用 visibleFrame.maxY 作为顶部。这是菜单栏下方的可用区域，不是物理屏幕上沿，因而黑框与屏幕顶边之间隔着菜单栏高度。poll() 检测到文件拖拽后立即展开面板，并不要求拖到顶部。普通屏幕上仍使用黑底和仅底部圆角的刘海式外观，就容易像突然出现的一块黑框。这是源码定位分析，尚未取得 mini 实际画面，不推断其他显示设置。

## 推荐：按屏幕采用两种入口

- 有刘海：保留现有刘海投放体验。
- 无刘海：使用贴着物理屏幕上沿中央的短投放栏，默认完全隐藏，只有文件拖到顶边中央感应区时展开。上边贴住屏幕，底边圆角；显示 PeerJetty 图标、默认目标和“松开发送”，避免看起来像假刘海。
- 首次设置和设置页说明“将文件拖到屏幕顶部中央发送”，保留现有预览按钮和选择文件发送入口。无需每天常驻黑框。
- 离开感应区且没有进入投放栏时收起；放下文件或取消拖拽后收起。传输状态优先保留在设置和通知中；错误或文件承诺需要交互时允许短暂显示状态，不遮住用户操作。
- 屏幕选择以开始拖拽时鼠标所在屏幕为准，不能总是优先 Air 的刘海屏。投放期间固定所在屏幕，避免跨屏移动时窗口跳动；下一次拖拽可选择另一块屏。
- 顶部感应区只在实际可接受的文件拖拽期间生效；不把普通鼠标经过或文本拖拽当成投放。

## 实施与验收

1. 将屏幕选择、感应区和面板坐标分开，使用 frame.maxY 计算真正的顶边；注意菜单栏区域不得常驻遮挡，显示时也只占中央短区域。
2. 区分刘海与普通屏幕的展开/收起规则，不影响正在传输、读取 File Promise 或错误提示的状态。
3. 验证普通屏幕、刘海屏、外接屏、多屏不同缩放、全屏/不同 Space、自动隐藏菜单栏、显示器重连及屏幕原点为负值。
4. mini 手工验证：无拖拽时无黑框；拖到中央顶边才展开；贴边且可接收拖拽；离开/取消/完成后收起；菜单和其他窗口仍可正常使用。

可选替代：可移动、可固定的小投放窗。它适合不喜欢顶部入口的使用者，但先不叠加更多设置；是否增加由贴边方案的实际试用决定。
