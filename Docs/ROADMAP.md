### 3. 文件与文本传输的可选动画

- [ ] 设置增加动画开关，覆盖文件与文本传输相关界面的出现／收起及成功反馈，让用户自行选择；默认值及是否细分开关待讨论。
- [ ] 动画风格、持续时间、触发时机和实现方式先商议，目标是贴近 macOS 的克制反馈，避免突兀跳动。
- [ ] 成功动画只在现有成功条件满足后出现；关闭动画时保留清楚的静态进度、结果和错误提示。

验收：中英文、小屏幕、有／无刘海布局、键盘与输入法、动画开／关及系统减少动态效果；Air／mini 实际观感与文件／文本收发待两机确认。沿用集中交付节奏，不为每一项单独发 Release。

## 2. 多语言支持（i18n）

internationalization 缩写为 i18n：i 与 n 之间有 18 个字母。它表示让程序具备适应多种语言/地区的结构；具体翻译与地区适配称为 localization（本地化，l10n）。

- [x] 文档先行：README 提供英文与简体中文，GitHub Release 说明双语；后续发布延续此约定。
- [x] 应用界面第一阶段：简体中文和英文，默认跟随系统语言。
- [x] 抽离窗口、菜单、按钮、通知、进度、错误、首次设置与配对提示中的固定文字。
- [x] 使用稳定的文字键和可翻译资源；不通过拼接片段构造句子。
- [x] 将系统权限说明也本地化；构建脚本正确复制 .lproj 等资源。
- [x] 当前采用 SwiftPM 加脚本组装 App，先选择适配此流程的资源方案，不要求为了翻译迁到完整 Xcode 工程。
- [x] 0.3.0 使用 stringsdict 处理收件数量与单复数，百分比随地区格式化，检查长文字布局和英文回退；目前界面没有文件大小／日期显示，增加这些字段时再本地化。
- [x] 显示语言不改变现有协议字段、设备身份、文件名或设备名称；拒收消息增加兼容的可选错误键与参数，保留旧版文字回退。
- [x] 两种语言下的隔离 TLS 传输与诊断兼容检查；旧字段与旧 JSON 解码兼容。
- [ ] 实机中文／英文两台设备互传、系统授权弹窗与各类实际错误路径验收。
- [x] 公开翻译贡献与语言选择说明，见 LOCALIZATION.md。
- [x] 0.3.1 增加应用内语言选择，自动保存本机偏好，退出重开生效；系统弹窗仍由 macOS 管理。

## 6. Windows 与 macOS 双向互传（已纳入计划，尚未实现）

2026-10-05 用户提出 Windows 客户端，并同意在可行时加入计划。技术上可行，但需要独立的 Windows 系统适配和实机验收；先完成 macOS 0.2.2 验收，再开展互通原型，不承诺下一版交付或固定日期。

### 首版范围与交互

- [ ] 首期聚焦 Windows 11 与现有 macOS 客户端，同一局域网、双向发送接收、设备配对、固定接收目录、自动接收已信任设备、收到只通知不自动打开。支持系统范围在技术验证后确认。
- [ ] 初版采用可拖入文件的普通窗口，辅以系统托盘入口和可配置快捷键召回投放面板；托盘图标不默认承担文件投放区。
- [ ] 可选择固定的小型投放窗口；屏幕边缘浮动入口作为后续可选设计，不默认在屏幕顶部突然弹出，也不模拟 Mac 刘海。
- [ ] 先支持 Explorer 拖入普通文件与文件夹及文件选择按钮；聊天软件的虚拟文件/承诺文件拖拽单独评估，不承诺与 macOS 首版完全相同。

### 阶段 A：先证明协议互通

- [ ] 验证 Windows DNS-SD 浏览、注册与解析能否发现现有 `_openonmini._tcp` 服务；明确防火墙、网络类型和多网卡行为。保留同认证规则的手动地址/端口连接，作为原型与发现失败时的替代入口。
- [ ] 在选定 TLS 库上验证 TLS 1.3、双端证书、证书指纹验证、ALPN 和 TLS exporter 的具体支持；特别核对当前配对协议依赖 exporter，不能只凭“支持 TLS”就认定可互通。
- [ ] 使用隔离测试身份验证六位配对码跨实现一致、双方确认、拒绝未授权设备、撤销信任，以及双向单文件传输、长度/hash 检查与保存确认。
- [ ] 形成固定协议测试向量和混合平台集成检查，以现有协议 v1 为共同约定；若确需调整协议，明确版本协商与旧版兼容，不直接替换通信标识。

### 阶段 B：Windows 客户端与文件安全

- [ ] 再选择 Windows 界面技术；C# / WinUI 3 可作为原生界面候选，网络实现根据阶段 A 的能力验证确定。此处尚未选定框架、TLS 库或第三方依赖。
- [ ] 适配设备私有身份的安全存储、通知、启动选项、接收目录授权、传输进度、取消与错误反馈；本机身份不进入 Git 或 Dropbox。
- [ ] 明确 Windows 文件名与文件系统差异：保留设备名、冒号等非法字符、末尾空格/点、大小写碰撞、路径长度、符号链接和 reparse points。无法表示的文件在预检中清楚拒绝；不静默改名或丢弃文件。
- [ ] 在 Windows 文件 API 上实现路径边界、排除链接逃逸、校验后提交、同名不覆盖以及取消清理；不能照搬 macOS 的 Darwin rename/O_NOFOLLOW 实现。
- [ ] 多根目录部分成功、断线重试以及文件正在变化时的语义与现有产品保持一致；跨平台权限/附加元数据的差异明确记录。

### 阶段 C：构建、发布与维护

- [ ] 初期继续使用同一个 PeerJetty 仓库；按平台组织代码与构建说明，共享协议、测试向量和产品规则。Windows 原型成熟后再调整目录，不为计划立即重排现有 macOS 项目。
- [ ] 保留 Swift/AppKit macOS 客户端，不为支持 Windows 立即整体重写。现有 PeerCore 使用 Apple 网络、身份与文件 API，不能直接编译成 Windows 版；是否提炼共享核心以后依据真实重复维护成本决定。
- [ ] 分开维护 macOS 与 Windows 的构建、安装包、签名/分发说明；产品功能版本协调，包名明确平台、架构与构建号，通信兼容性由协议版本单独管理。
- [ ] Windows 自动检查 + macOS 自动检查 + 混合双机验收；覆盖配对/撤销、双向文件夹、非法路径、同名冲突、断线、睡眠恢复与网络变化。
- [ ] 首次提供 Windows 包时标为预发布，维护清楚的支持范围；应用内更新也需分别设计平台适配。

难度判断：普通拖拽窗口中等；安全、兼容的混合平台客户端中高；接近各平台原生体验、可靠安装和持续维护高。局域网发现和刘海并非主要阻碍，安全协议实现、文件系统差异和跨平台验收才是工作重点。这是工程估计，不是已完成验证。
